## 概念

### 1. 自动化测试的两大类

- **UI 自动化**：模拟人在界面上操作，比如打开网页、在输入框里填内容、点按钮，再检查页面上出现了什么。常用工具有 Selenium、Playwright。缺点是慢，而且界面一改，脚本就容易坏。
- **接口自动化**：不经过界面，直接给后端接口发请求，检查返回的数据。速度快、稳定，界面怎么改都不影响，是自动化测试里性价比最高的一类。

拿短链接的“生成短链接”功能来比较：

- UI 自动化：打开网页，在输入框填 `https://www.python.org`，点“生成”按钮，检查页面上有没有出现短链接
- 接口自动化：直接发一个 `POST /shorten` 请求，检查返回的 JSON 里有没有 `code` 字段

### 2. Python 接口自动化：5 个模块加 1 个框架

| 工具 | 作用 |
| --- | --- |
| `requests` | 发 HTTP 请求 |
| `yaml` | 把测试数据写在配置文件里，和代码分开 |
| `jsonschema` | 一次性校验返回数据的结构 |
| `logging` | 记录日志，出问题时方便排查 |
| `allure` | 生成好看的测试报告 |
| `pytest` | 测试框架，负责组织和执行所有用例 |

**requests：发请求**

```python
import requests

resp = requests.post(
    "http://127.0.0.1:8000/shorten",
    json={"url": "https://www.python.org"},
)
print(resp.status_code)  # 200
print(resp.json())       # {'code': 'aZ3k9Q', 'short_url': 'http://127.0.0.1:8000/aZ3k9Q'}
```

**yaml：测试数据和代码分开**

把要测的数据写进 `cases.yaml`，以后加用例只改这个文件，不用动代码：

```yaml
- name: 合法网址
  url: https://www.python.org
  expected_status: 200
- name: 不是网址
  url: abc
  expected_status: 422
- name: 空字符串
  url: ""
  expected_status: 422
```

Python 里用 PyYAML 读出来，得到的就是一个列表：

```python
import yaml

with open("cases.yaml", encoding="utf-8") as f:
    cases = yaml.safe_load(f)
```

**jsonschema：校验返回结构**

如果一个字段一个字段地写 `assert`，返回数据一复杂就写不过来了。JSON Schema 是一份“返回数据应该长什么样”的说明，一行就能校验完：

```python
from jsonschema import validate

schema = {
    "type": "object",
    "required": ["code", "short_url"],
    "properties": {
        "code": {"type": "string", "pattern": "^[A-Za-z0-9]{6}$"},
        "short_url": {"type": "string"},
    },
}

validate(instance=resp.json(), schema=schema)  # 不符合就抛出 ValidationError，测试失败
```

这里规定了：返回必须是一个对象，必须有 `code` 和 `short_url`，而且 `code` 必须是 6 位字母或数字。

**logging：记录日志**

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger(__name__)

log.info("请求 POST /shorten，请求体=%s", {"url": "abc"})
log.info("返回 %s %s", resp.status_code, resp.text)
```

比 `print` 好的地方是：自带时间，能分级别（`INFO`、`WARNING`、`ERROR`），还能写进文件。用例失败时翻日志，就能看到当时到底发了什么、收到了什么。

**allure：测试报告**

```
pip install allure-pytest
pytest --alluredir=allure-results
allure serve allure-results
```

最后一行要先装 Allure 命令行工具（它依赖 Java）。它会在浏览器里打开一份网页报告，有通过率、每个用例的步骤和耗时。

**pytest：把上面这些串起来**

```python
import pytest
import requests
import yaml

BASE_URL = "http://127.0.0.1:8000"

with open("cases.yaml", encoding="utf-8") as f:
    CASES = yaml.safe_load(f)


@pytest.mark.parametrize("case", CASES, ids=[c["name"] for c in CASES])
def test_shorten(case):
    resp = requests.post(f"{BASE_URL}/shorten", json={"url": case["url"]})
    assert resp.status_code == case["expected_status"]
```

`@pytest.mark.parametrize` 是“参数化”：yaml 里有几条数据，这个测试就自动跑几遍，每一遍用一条数据。这种写法叫**数据驱动**。

### 3. 接口是什么

接口分两种：

- **程序内部的接口**：函数和函数之间、模块和模块之间的调用约定。比如短链接项目里，`shorten()` 会调用 `generate_code(conn)`，约定好“传进一个数据库连接，返回一个没被用过的短码”，这就是内部接口。
- **系统对外的接口**：系统专门开放给外部调用的入口。别的网站不会把数据库直接给你，而是提供写好的接口让你调用。比如别人不能直接读我放在 Neon 上的数据库，只能通过 `POST /shorten` 生成短链接、通过 `GET /stats/{code}` 查统计。

接口的类型也有很多，最常见的两种：

- **HTTP API**：通过 HTTP 请求调用，数据一般是 JSON，我的短链接用的就是这种
- **RPC 接口**：远程过程调用，让你调用另一台机器上的函数，写起来就像调用本地函数一样，常见的有 gRPC、Dubbo，多用在公司内部的服务之间

### 4. 一份规范的接口文档

测试之前，先要明确有哪些接口，而接口文档就是依据。以我的短链接接口为例：

**接口说明**：把一个长网址转换成短链接

**调用 URL**：`/shorten`

**请求方法**：`POST`

**请求参数**（请求体，JSON 格式）：

| 参数名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `url` | string | 是 | 要缩短的原始网址，必须是合法的 http 或 https 地址 |

**返回示例**：

```json
{"code": "aZ3k9Q", "short_url": "https://xxx.onrender.com/aZ3k9Q"}
```

**错误码**：`url` 缺失或格式不对时返回 `422`。

FastAPI 会根据代码自动生成这样的文档，就是 `/docs` 那个页面。

### 5. 前端校验不能代替后端校验

前端的输入框可以用 JavaScript 检查“输入的是不是网址”，但这只能防住老老实实用网页的人。任何人都可以绕过网页，用 `requests` 直接调接口：

```python
requests.post("https://xxx.onrender.com/shorten", json={"url": "abc"})
```

如果后端不检查，`abc` 就会被存进数据库。我的短链接在后端用 Pydantic 的 `HttpUrl` 做了校验，所以这个请求还是会被拒绝，返回 `422`。

结论：**前端校验是为了用户体验，后端校验才是真正的防线**。测试时两边都要测，尤其是要专门绕过前端去测后端。

### 6. 常见状态码

| 状态码 | 含义 | 例子 |
| --- | --- | --- |
| 200 | 成功 | 生成短链接成功 |
| 201 | 创建成功 | 很多接口新建资源后返回它 |
| 301 / 302 / 307 | 重定向 | 访问短链接时返回 307，跳到原网址 |
| 400 | 请求有误 | 请求格式本身有问题 |
| 401 | 未认证 | 没登录就调用需要登录的接口 |
| 403 | 没有权限 | 登录了，但没权限做这件事 |
| 404 | 找不到 | 访问一个不存在的短码 |
| 422 | 参数校验失败 | `url` 填了 `abc`（FastAPI 很常见） |
| 500 | 服务器内部错误 | 代码出了 bug 或者数据库连不上 |
| 502 / 503 | 网关错误 / 服务不可用 | 服务挂了或者正在重启 |

### 7. 用例设计分两步走

1. **从单个接口出发设计**：看接口文档，针对每个接口的输入和输出设计用例，比如 `/shorten` 传各种各样的 `url`
2. **结合业务逻辑设计**：把多个接口串成一个真实的使用流程来测。比如：

   生成短链接 → 访问 3 次 → 查统计 → 检查 `clicks` 等于 3

   单看每个接口都没问题，不代表串起来也没问题，业务流程测试就是为了发现这类问题。

### 8. 接口用例怎么写

以 `POST /shorten` 为例：

**通过性验证**：正常的请求能不能正常工作

| 用例 | 请求体 | 预期 |
| --- | --- | --- |
| 合法网址 | `{"url": "https://www.python.org"}` | 200，返回 6 位 `code` |

**参数组合**：各种不正常的参数

| 用例 | 请求体 | 预期 |
| --- | --- | --- |
| 缺少必填参数 | `{}` | 422 |
| 类型错误 | `{"url": 123}` | 422 |
| 格式错误 | `{"url": "abc"}` | 422 |
| 空值 | `{"url": ""}` | 422 |
| 超长网址 | 一个 1 万字符的网址 | 不应该让服务器崩溃 |
| 多余参数 | `{"url": "https://a.com", "admin": true}` | 多余参数被忽略，不产生任何影响 |

**接口安全**：

- **绕过前端、伪造参数**：像上面第 5 点那样，直接调接口传前端不允许的值
- **越权**：假设以后加一个删除接口 `DELETE /links/{code}`，用户 A 能不能删掉用户 B 的短链接？这叫水平越权。普通用户能不能调用管理员才能用的接口？这叫垂直越权。
- **隐私数据**：返回的数据里有没有不该给的信息。我的短链接现在就有这个问题：任何人都能查任何短码的 `/stats`，访问数据没有任何保护。
- **注入攻击**：比如把短码填成 `x' OR '1'='1`，测试会不会发生 SQL 注入。我的代码用了参数占位符，所以不会。

### 9. 接口自动化测试的 8 步流程

用我的短链接走一遍：

1. **需求分析**：短链接服务要能生成短链接、跳转、统计访问次数
2. **挑选要自动化的接口**：时间紧的时候，先保证重要的接口，再尽量多覆盖。挑选标准是功能复杂、风险高、需要反复执行。
   - `POST /shorten`：核心功能，最先做
   - `GET /{code}`：风险高，跳转功能可能被人用来做钓鱼链接
   - `GET /stats/{code}`：相对次要，放在后面
3. **设计测试用例**：就是上面第 8 点的表格
4. **搭建测试环境**：本地启动服务，连测试用的数据库，绝对不要直接测线上 Neon 里的真实数据
5. **设计自动化框架**：规划好目录结构，比如：

   ```
   api_tests/
   ├── cases/shorten.yaml     # 测试数据
   ├── common/client.py       # 封装 requests 和 logging
   ├── conftest.py            # pytest 的公共准备工作
   ├── test_shorten.py        # 测试用例
   └── pytest.ini             # pytest 配置
   ```

6. **编写代码**：按框架写用例
7. **执行测试用例**：用 pytest 跑，比如 `pytest -v`
8. **生成测试报告**：用 allure 生成报告，看通过率和失败原因
