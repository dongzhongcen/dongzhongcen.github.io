## 1 什么是 MQ

### 1.1 MQ 的定义

<span style="color:#e03131">MQ（Message Queue，消息队列）是在消息传输过程中保存消息的容器</span>，本质上是一个队列，遵循先进先出（FIFO），只不过队列里放的是“消息”。

- **生产者（Producer）**：发送消息的一方
- **消费者（Consumer）**：接收并处理消息的一方
- **MQ 服务器（Broker）**：夹在中间，负责<span style="color:#e03131">接收消息、存储消息、转发消息</span>

<span style="color:#e03131">MQ 多用于分布式系统之间的通信。</span>一个大系统被拆成很多个服务（用户服务、订单服务、库存服务……）以后，服务之间要互相传递数据，MQ 就是其中一种通信方式。

### 1.2 同步通信与异步通信

分布式系统之间的通信有两种方式：

| 方式 | 含义 | 生活中的例子 | 技术上的例子 |
| --- | --- | --- | --- |
| <span style="color:#e03131">同步通信</span> | 调用方发出请求后，必须等对方处理完、拿到结果才能继续往下走 | 打电话：对方必须接听，你要一直拿着电话等对方说完 | HTTP 远程调用，比如用 OpenFeign、RestTemplate 调另一个服务的接口 |
| <span style="color:#e03131">异步通信</span> | 调用方把消息交给中间人就返回，不等对方处理，对方有空了再去处理 | 发微信：消息发出去你就去干别的了，对方什么时候看、什么时候回都行 | 基于 MQ 的消息通信 |

![同步通信与异步通信结构对比](/assets/img/mq/mq-sync-vs-async.svg)

**图解：** 两个例子做的是同一件事：用户注册成功后，要写数据库、发欢迎邮件、发短信。

- **（a）同步**：用户 → 注册服务 → 邮件服务 → 短信服务排成一条链。实线箭头是发出请求，虚线箭头是等待对方返回结果。注册服务必须等邮件发完、短信发完才能告诉用户“注册成功”，耗时是三步加起来。<span style="color:#e03131">只要链上任意一个服务变慢或挂掉，注册就会跟着变慢或失败</span>，服务之间绑得很紧，这叫“耦合”。
- **（b）异步**：注册服务写完数据库后，往 MQ 里放一条“注册成功”的消息，就立刻返回给用户（红色虚线）。邮件服务和短信服务是消费者，各自从 MQ 里取消息再去干活（绿色箭头）。用户只需要等写库和发消息的时间。<span style="color:#e03131">生产者和消费者互相不等待、也不需要知道对方是谁</span>，邮件服务就算暂时挂了，消息也还在 MQ 里，恢复后照样能处理。
- 图里的 50ms 只是举例，用来对比两种方式的差别。

**同步和异步的优缺点：**

| | 优点 | 缺点 |
| --- | --- | --- |
| 同步通信 | 时效性强，能立即拿到结果 | 耦合度高；性能和吞吐量差（要一直等）；有额外的资源消耗；容易出现级联失败（一个服务挂了，调用它的服务跟着挂） |
| 异步通信 | 耦合度低、扩展性强；无需等待，性能好；故障隔离；可以缓存消息，流量削峰 | 不能立即得到调用结果，时效性差；不确定下游业务是否执行成功；业务安全依赖于 MQ 的可靠性 |

## 2 MQ 的作用

MQ 的工作说到底就一件事：<span style="color:#e03131">接收并转发消息</span>。基于这一点，它在实际项目中有下面几种典型用途。

### 2.1 异步解耦

**例子：用户注册完成后发送邮件。**

注册是主业务，发邮件、发短信、送新人优惠券都是附加业务。如果全部同步调用，注册服务就要依赖一大堆其他服务，每加一个新需求都要改注册服务的代码。

用 MQ 以后，注册服务只负责发一条“用户注册成功”的消息，谁关心这件事谁就自己订阅。<span style="color:#e03131">主业务和附加业务被拆开了，一方的变化和故障不会影响另一方</span>。结构就是上面的图（b）。

### 2.2 流量削峰

**例子：买票、秒杀。**

![流量削峰示意图](/assets/img/mq/mq-peak-shaving.svg)

**图解：** 横轴是时间，纵轴是请求量，橙色虚线是后端系统每秒最多能处理的请求数。

- **左图（没有 MQ）**：放票那一刻请求量（红线）突然冲到远高于系统处理能力的位置，超出的部分系统扛不住，轻则响应极慢，重则直接宕机。
- **中间（MQ 缓冲）**：所有请求先进 MQ 排队，MQ 能扛住大量消息的堆积。
- **右图（有 MQ）**：后端按自己的能力从 MQ 里匀速取消息处理（蓝线），最高也只到处理能力那条线，高峰被“削”成了一段平台，持续时间拉长了。
- <span style="color:#e03131">代价是高峰期的请求要排队，用户会等得久一点，但系统不会被压垮。</span>

### 2.3 消息分发

**例子：支付成功。**

![消息分发示意图](/assets/img/mq/mq-dispatch.svg)

**图解：** 左边的支付服务是生产者，用户付款成功后，它只往 MQ 发一条“支付成功”的消息（橙色箭头）。右边四个绿色框都是消费者，同一条消息被分发给它们（绿色箭头），各自做自己的事：

- 订单服务：把订单状态改成“已支付”
- 库存服务：扣减库存
- 积分服务：给用户加积分
- 通知服务：给用户发短信或推送

<span style="color:#e03131">支付服务不需要知道有哪些系统关心“支付成功”</span>。以后要加一个“物流服务”，只要让它也订阅这条消息就行，支付服务的代码一行都不用改。

### 2.4 延时通知

**例子：下单 30 分钟内未支付，自动取消订单。**

![延时通知示意图](/assets/img/mq/mq-delay.svg)

**图解：** 用户下单后，订单服务往 MQ 的<span style="color:#e03131">延时队列</span>里发一条消息，设定 30 分钟后才投递（橙色箭头）。30 分钟到了，MQ 把消息送回订单服务（绿色箭头），订单服务检查这笔订单：

- 已经支付：什么也不做
- 还没支付：取消订单，把锁定的库存释放出来

如果没有 MQ，就得写一个定时任务，每隔一分钟扫一遍数据库找超时订单，既浪费资源，时间也不精确。

### 2.5 其他作用

- **日志收集**：各个服务把日志发到 MQ，再统一写入日志系统（Kafka 最常见的用法）
- **数据同步**：数据库的数据变化通过 MQ 通知搜索引擎、缓存等，让它们跟着更新
- **分布式事务**：借助 MQ 的可靠消息，保证多个服务的数据最终一致（后面学到再细说）

## 3 三大主流 MQ

### 3.1 Kafka

- 由 LinkedIn 开发，2011 年开源，后来成为 Apache 顶级项目，用 Scala 和 Java 编写
- <span style="color:#e03131">最初就是为了日志收集和传输而设计的</span>，追求高吞吐量，性能卓越
- <span style="color:#e03131">大数据领域、日志采集的首选</span>
- 缺点：功能相对简单，消息的可靠性和实时性不如 RabbitMQ；单机队列（分区）太多时性能会下降

### 3.2 RocketMQ

- 由阿里巴巴开发并开源，后来捐给 Apache，成为顶级项目，<span style="color:#e03131">用 Java 编写</span>
- 借鉴并改进了 Kafka 的设计，经历过淘宝“双十一”的考验
- 优点：<span style="color:#e03131">可靠、可用、稳定，能扛高并发</span>，适合电商、金融这类对可靠性要求高的业务；Java 写的，Java 程序员读源码、定制都方便
- 缺点：<span style="color:#e03131">支持的客户端语言不多</span>（以 Java 为主），社区活跃度一般，网上能找到的解决方案相对较少

### 3.3 RabbitMQ

- <span style="color:#e03131">用 Erlang 编写</span>，基于 AMQP 协议
- 优点：<span style="color:#e03131">功能完善</span>，路由灵活，有好用的管理界面；<span style="color:#e03131">社区活跃度高，遇到问题容易找到答案</span>，解决问题难度较低；延迟很低
- 缺点：<span style="color:#e03131">吞吐量相较于前两者差</span>；Erlang 语言小众，想深入看源码、二次开发比较难

### 3.4 对比与选择

| 对比项 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 开发语言 | Scala / Java | Java | Erlang |
| 单机吞吐量（常见说法） | 百万级 | 十万级 | 万级 |
| 消息延迟 | 毫秒级 | 毫秒级 | 微秒级 |
| 可靠性 | 一般 | 高 | 高 |
| 功能 | 简单，专注吞吐 | 较完善 | 最完善 |
| 社区活跃度 | 高 | 一般 | 高 |
| 典型场景 | 日志采集、大数据 | 电商、金融等高并发业务 | 中小规模业务、对可靠性和功能要求高的场景 |

吞吐量这一行是网上和课程里常见的量级说法，实际数值取决于配置、硬件和消息大小，只用来比较三者的相对高低。

<span style="color:#e03131">怎么选：</span>做日志收集、大数据选 Kafka；并发量特别大、又要高可靠选 RocketMQ；一般的业务系统、想要功能全和问题好查，选 RabbitMQ。

## 4 RabbitMQ 介绍

### 4.1 RabbitMQ 是什么

<span style="color:#e03131">RabbitMQ 是一个用 Erlang 语言开发、基于 AMQP 协议的开源消息中间件。</span>

- **AMQP**（Advanced Message Queuing Protocol，高级消息队列协议）：一个应用层的开放标准协议，规定了消息怎么发、怎么路由、怎么确认。只要遵守这个协议，不同语言、不同厂商的客户端和服务器就能互通，就像 HTTP 之于浏览器和网站。
- **Erlang**：爱立信为电信系统设计的语言，<span style="color:#e03131">天生擅长高并发和分布式</span>，所以 RabbitMQ 稳定、延迟低。

### 4.2 简要历史

| 时间 | 事件 |
| --- | --- |
| 2003 年起 | 摩根大通（JPMorgan Chase）为了让金融系统之间可靠地传递消息，发起了 AMQP 协议，后来多家公司一起制定成开放标准 |
| 2007 年 | Rabbit Technologies 公司发布 RabbitMQ 的第一个版本，它是最早实现 AMQP 的开源产品之一 |
| 2010 年 | Rabbit Technologies 被 VMware 旗下的 SpringSource 收购，RabbitMQ 和 Spring 从此关系密切（后来有了 Spring AMQP） |
| 2013 年 | 随 VMware 的相关业务并入 Pivotal 公司 |
| 2019 年 | VMware 收购 Pivotal，RabbitMQ 又回到 VMware 旗下 |
| 2023 年 | 博通（Broadcom）收购 VMware，RabbitMQ 现在由博通旗下的团队维护，仍然是开源项目 |

### 4.3 RabbitMQ 的特点

- **可靠性**：支持消息持久化、发送确认、消费确认，尽量保证消息不丢
- **灵活的路由**：消息先发给交换机（Exchange），再由交换机按规则路由到队列，内置多种交换机类型
- **集群和高可用**：多台 RabbitMQ 可以组成集群，队列可以在多个节点上做副本
- **多协议**：除了 AMQP，还支持 MQTT、STOMP 等协议
- **多语言客户端**：Java、Python、Go、C#、JavaScript 等几乎所有常用语言都有客户端
- **管理界面**：自带网页管理后台，能直接看队列、消息、连接情况
- **插件机制**：比如延时消息插件、Web STOMP 插件，可以按需扩展

### 4.4 先认识几个核心概念

后面的笔记会详细学，这里先混个脸熟：

| 概念 | 含义 |
| --- | --- |
| <span style="color:#e03131">Producer</span> | 生产者，发送消息的程序 |
| <span style="color:#e03131">Consumer</span> | 消费者，接收消息的程序 |
| <span style="color:#e03131">Broker</span> | 就是 RabbitMQ 服务器本身 |
| <span style="color:#e03131">Exchange</span> | 交换机，接收生产者的消息，按规则转发给队列，自己不存消息 |
| <span style="color:#e03131">Queue</span> | 队列，真正存放消息的地方，消费者从这里取消息 |
| Binding | 绑定，交换机和队列之间的路由规则 |
| Virtual Host | 虚拟主机，相当于一个独立的小 RabbitMQ，用来隔离不同项目 |
| Connection / Channel | 连接和信道，客户端和 Broker 之间的 TCP 连接，以及在一个连接里开的多个轻量通道 |

消息流转的路线是：<span style="color:#e03131">生产者 → 交换机 → 队列 → 消费者</span>。

### 4.5 同类产品

| 产品 | 简介 |
| --- | --- |
| ActiveMQ | Apache 出品，Java 编写，支持 JMS 规范，老牌 MQ，现在新项目用得越来越少 |
| Kafka | 见 3.1，高吞吐，日志和大数据首选 |
| RocketMQ | 见 3.2，阿里开源，高并发高可靠 |
| Pulsar | Apache 项目，存储和计算分离的新一代消息系统，同时支持消息队列和流处理 |
| ZeroMQ | 严格说是一个高性能的网络通信库，不是独立的 MQ 服务器，需要自己在程序里实现队列逻辑 |

## 本章小结

```text

│   ├── 同步通信：要等结果，时效性强，但耦合高、性能差、易级联失败
│   └── 异步通信：发完就走，解耦、性能好、故障隔离，但拿不到即时结果

│   ├── 异步解耦：注册成功后发邮件
│   ├── 流量削峰：买票、秒杀

│   └── 其他：日志收集、数据同步、分布式事务
├── 三大主流 MQ
│   ├── Kafka：日志采集首选，吞吐量最高
│   ├── RocketMQ：Java，阿里开源，可靠稳定、并发大，客户端语言少
│   └── RabbitMQ：Erlang，功能完善、社区活跃，吞吐量相对低

    ├── Erlang 开发、基于 AMQP 协议的开源消息中间件

```
